Facebook Pipeline

Pulling Facebook Page posts through the Graph API — media, engagement, and reaction breakdowns — for broadcast and multimedia analytics.

Author — Your Name Mentor — Amaan Irfan Faculty Advisor — Prof. Prithwijit Guha

Introduction

What this project does

This pipeline connects to a Facebook Page through the Graph API and pulls its posts — including the media attached to each one (photo, video, album, or link), the reaction breakdown across all six reaction types, comment and share counts — so the data can be used for downstream broadcast and multimedia analytics. It mirrors the structure of the existing Twitter pipeline (config.py / twitter_client.py), with a Facebook-specific client (facebook_client.py) built on the same credential-loading pattern.

Architecture

How a post moves through the pipeline

Two stages: getting credentialed access to a Page, and the client pipeline that pulls, saves, and normalizes its posts.

PHASE A — CREDENTIALS & ACCESS

  1. Test Page

    Created a Facebook Page to administer, and posted sample content (text, image, link) so the pipeline has real data to pull once working.

  2. Meta for Developers account

    Registered at developers.facebook.com using the existing test Facebook account.

  3. Meta App

    Created via My Apps → Create App, use case "Other", type "Business" — generates the App ID and App Secret.

  4. Development Mode

    Left in Development Mode rather than submitted for App Review — any user with a role on the app can generate tokens and pull data immediately.

  5. User Access Token

    Generated in Graph API Explorer with pages_show_list, pages_read_engagement, pages_read_user_content permissions.

  6. Long-lived Page Access Token

    Short-lived User token (~1–2 hrs) exchanged via the Access Token Debugger / /oauth/access_token (grant_type=fb_exchange_token) into a ~60-day token, then /me/accounts returns the Page Access Token the pipeline actually uses.

  7. Verified with one real request

    GET /{page-id}/posts?fields=message,created_time,likes.summary(true),comments.summary(true),shares in Graph API Explorer, confirming real JSON came back before writing any client code.

  8. Credentials saved

    FACEBOOK_APP_ID, FACEBOOK_APP_SECRET, FACEBOOK_PAGE_ID, FACEBOOK_PAGE_ACCESS_TOKEN in .env, loaded the same way twitter_client.py loads TWITTER_API_KEY.

PHASE B — CLIENT PIPELINE

  1. API version + token check

    Bumped the expired v18.0 endpoint to a current stable version, and check the Page Access Token hasn't expired (Access Token Debugger) before assuming a failure is version-related.

  2. Expand requested fields

    Moved beyond id,message,created_time to include attachments (media type/URL — the multimedia classification signal), six aliased reactions.type(X) calls for the full reaction breakdown, and likes.summary(true) for a cheap total count.

    shares only appears in the response when a post has ≥1 share — parsed as post.get("shares", {}).get("count", 0), not a direct key lookup.

  3. Pagination

    Follow paging.next until it disappears; once following it, don't re-pass params (the URL already encodes them). limit=100 is the practical max Facebook honors per request.

  4. Raw-save stage

    Every unmodified API response now lands on disk before any transform — the source of truth for reprocessing without re-hitting a rate-limited API, and a hedge against Meta renaming fields later.

  5. Error handling by Facebook error code

    Split from one generic RuntimeError into code-specific handling (table below), so the pipeline can tell "wait and retry" from "stop and alert" from "fix the config."

  6. Multiple Pages + scheduling

    Page IDs moved out of a hardcoded .env entry into pages.txt (one ID per line), looped over. Scheduling is a simple interval loop — no job scheduler needed at this scale.

    One Page Access Token only works for Pages you administer — a pages.txt entry you don't admin fails with 190/permission, which is a platform limit, not a bug to fix.

  7. Downstream: flatten + store

    Each raw post dict is normalized into a row — post_id, page_id, message, created_time, media_type, media_url, the six reaction counts, comment_count, share_count — and ingested into SQLite for querying.

Error-code routing

FACEBOOK GRAPH API ERROR CODES → PIPELINE RESPONSE
CodeMeaningResponse
190Access token expired or invalidStop the run, alert — a fresh token is needed, not a retry
4, 17App / user rate limit hitBack off and retry later
10, 200, 294Missing permission / unscoped fieldConfig problem — fix the field list
100Invalid parameter (malformed field string)Request bug — will never succeed on retry
